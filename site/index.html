Know what is safe to remove.

PruneDisk is a free, open-source disk analyzer and cleaner for Windows, macOS and Linux that works out what each folder on a developer machine actually is, and therefore what can be removed, what must be backed up first, and what must be left alone.

The problem

A developer disk fills up in a particular way. Hundreds of clones. Forty linked worktrees an agent created and never tidied. A node_modules or target folder in every project you have ever touched. Package caches. Gigabytes of coding-agent transcripts and logs. Rendered videos and model files that were never meant to go into git.

A general disk tool shows you one big folder and leaves the judgement to you. The risky part is that the folder next to it may hold the only copy of an unpushed branch, a stash, or a .env file. PruneDisk is being built to tell those cases apart before anything is touched.

How it decides what is safe

Every directory gets one class. Each class has a default disposition. These are the rules in the project's design document; the read-only scanner in review assigns repo, worktree, bare-repo, regenerable, cache and loose-code, and lists output files individually. Agent-session handling is designed but not built.

Classes and what happens to them by default
ClassWhat it isDefault
repoA directory with a .git directory.Keep. Can be archived when idle and fully on a remote.
worktreeA linked git worktree.Like a repo, checked against its own HEAD.
bare-repoA bare git repository.Never removed while a worktree or clone depends on it.
regenerablenode_modules, target, .venv, .next, DerivedData.Remove when the owning project is not active.
cachePackage manager and tool caches.Remove by age or size policy.
agent-sessionCoding-agent transcripts, logs and work directories.Back up first, remove only after a verified backup and an age threshold.
outputVideo, audio, images, archives, model weights, datasets.Never to git. Back up, then remove by policy.
loose-codeSource files or a project manifest outside any repo.Ask: connect a remote, back up, remove, or leave.
system, user-dataOperating system files, documents, photos.Analyze only.

What it checks before it calls a repo safe

For every repo and worktree the scanner records seven facts. Each is yes, no or unknown. Unknown never counts as yes: a check that fails or times out means keep.

  • It has at least one network remote. A local path or a bundle file is not a backup.
  • The checked-out commit is on a remote branch, including a detached HEAD.
  • Every local branch is on a remote. A repo with local tags stays unknown until the remote itself is asked.
  • The stash is empty.
  • The working tree is clean: no changes and no untracked files.
  • There are no ignored files that exist only here, such as .env or a local database.
  • No other clone or worktree depends on this one.

A repo is safe to remove only when all seven are yes. Anything else is ambiguous, and the plan says so. Remote facts come from local remote-tracking refs, which can be stale, so the plan marks them unverified. Re-checking them against the live remote at the moment of removal is planned for the step that applies a plan.

Plan, then apply

Scanning and planning are read-only. A plan is a file you can read and edit. Apply, when it exists, will do exactly that plan.

Everything removed is findable

The design writes each removal to a manifest with a restore command. That part is planned, not built.

Follow along

The project is developed in the open. The best way to follow it is the repository: the design document, the open pull request for the scanner, and the issue tracker. The repository is still named disk-cleaner; renaming the repository and the command to prunedisk is planned, not done. There is no mailing list, no account to create and nothing to install yet.
